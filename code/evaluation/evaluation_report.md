# Evaluation report

Generated by `python3 code/evaluation/main.py`. Everything in the tables below is computed from the run being reported; do not edit the numbers by hand.

## 1. Method

The pipeline is evaluated on the 32 public samples (`dataset/sample_deletion_requests.csv` against `dataset/sample_output.csv`), on custom cases built from those samples, and for sanity on the full 518-request set (which has no reference answers).

Metric definitions:

- **Status accuracy:** predicted `deletion_status` equals the reference.
- **Step accuracy:** a step is identified by `(phase, operation, system_id, resource_id)`; precision and recall are micro-averaged over all cases. *Strict* also requires the same `evidence_id`.
- **Field accuracy:** step `i` of the prediction is compared with step `i` of the reference, field by field; missing or surplus positions count as wrong for every field, so one missing step also shifts the steps after it.
- **Sequence accuracy:** the ordered list of step identities is identical to the reference. Sequence similarity is `2 * LCS / (expected + predicted)`, which only penalizes the steps that are out of order or absent.
- **Exact row:** status and all steps (including `step_no` and `evidence_id`) equal the reference.

Caveat: the pipeline was developed against these 32 samples, so the sample numbers are optimistic; there is no independent reference for the 518 evaluation requests.

## 5. Failures found

1. **Partial account coverage via the `reported_at` window.** `account_service` records carry no email, phone or hash, so they cannot be linked to a person by content. The investigator accepts the single account `DELETE_RECORD` activity within -90/+20 minutes of the case's `reported_at`. Accounts whose delete event falls outside that window, or where several deletes compete, are not found, which removes the `account_service` verification (and finding, when still present) from those answers (for example case_04).

2. **Anonymized analytics linked by a second-of-minute heuristic.** Anonymized analytics profiles contain no identifier either. They are linked through the activity stream: the profile deletion appears 40-42 seconds after the account delete. This matches every sample that has one, but it is a regularity of the data, not a documented rule, so an analytics record with a different offset would be missed.

3. **Ids that appear in no visible source.** Some reference steps use resource ids (mostly security audit records and some accounts) that exist in no participant-visible file or activity. The planner never invents ids, so those steps are omitted. Each such case loses recall but never produces a wrong citation.

4. **case_17 decoy (`account_6523`).** A debug log of a profile lookup dated 2026-03-10 (`lookup_key` is the requester's email, result `rows=0 http_status=404`) names `account_6523`. The investigator links the resource through the email and adds an account verification that the reference does not contain: one surplus step in a single sample case. The lookup predates the request by months and found no row, so the reference most likely treats it as a decoy; this is an inference, since the reference gives no reason. Status and every other step of the case are correct.

5. **Cited evidence file is not unique.** A resource is usually visible in several snapshots. The reference cites one specific file and its choice is not recoverable from the visible data; the planner cites the latest valid observation captured at or before `audit_at`, preferring a file shared by most resources of the case. Steps that match on resource and operation can therefore still differ in `evidence_id`; this is why strict step accuracy is lower than step accuracy.

6. **Intent classification falls back to rules when the provider is unavailable.** A request text is classified by the model, and every accepted answer is cached. When the provider's daily token quota is exhausted, texts missing from the cache are classified by a multilingual keyword fallback instead (section 4 counts the texts decided by each source in the reported run). During development 31 texts, including the 10 non-deletion requests, were decided by the fallback for that reason. After the quota reset the model classified them, the answers were cached, and the 518 output rows did not change, so the fallback agreed with the model on those texts. The fallback remains a risk for any new, differently worded request: it can miss a negation or a language it has no keywords for.

## 6. Improvements made

- **Time cutoff everywhere.** Evidence, activities and audit events later than `audit_at` are dropped at every stage, and the planner only cites ids that were visible at `audit_at` (checked on all 518 answers below).
- **Claims are not proof.** A `SUCCESS` activity is only accepted as a state when evidence shows the resulting state; `CHECK_*`, `SYNC_*` and `RESTORE_*` activities are used to detect active flows, restore paths and recreation after a deletion.
- **Account lookup anchored on `reported_at`.** Accounts have no identifiers, so the single account `DELETE_RECORD` activity near `reported_at` is used instead of guessing across the whole stream.
- **Support evidence classification.** Contact-index lookups map to `SECONDARY_IDENTIFIER` (delete) and business documents to `SUPPORT_ATTACHMENT` (delete) instead of `SUPPORT_MESSAGE` (redact); this fixed the policy treatment of case_07 and case_10.
- **Contract ordering.** Steps are ordered phase, operation table order, `system_id`, `resource_id`, with consecutive `step_no`, and natural `case_id` order (`case_2` before `case_10`); the writer validates everything before touching `output.csv`.
- **Fixed-step fallback.** The account and security-audit verifications that every deletion case has are emitted from whatever ids were found and are skipped, never invented, when none exist.
- **Reproducible LLM use.** Every accepted model answer is cached by a hash of provider, model, prompts and image bytes, so a second run makes no provider call; after the first provider failure the intent classifier stops calling the provider and uses the cache plus the keyword fallback.
- **Prompt-injection hardening.** Request text is sent only inside `<request>` tags with an instruction to treat it as data, and nothing else from the case is sent to the model (see custom case 4).
